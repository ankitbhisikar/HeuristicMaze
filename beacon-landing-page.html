Ownership-aware routing

Most paging tools ask a human to maintain a rotation and hope it's current. Beacon reads your service graph and git history, so an alert on the checkout service pages whoever actually owns checkout — this week, not last quarter.

  • Ownership inferred from deploy history and code paths, kept current automatically
  • Falls back cleanly through a rotation if the owner is unreachable
  • Shows the responder the last three deploys before they even open a laptop

Set rules in code, not a settings page

Escalation policies live in a config file next to your service definitions, reviewed in pull requests like everything else. No more archaeology through a UI to figure out why an alert went to the wrong person at 3 a.m.

  • Version-controlled escalation policies, one per service
  • Test a policy against last month's real alerts before it goes live
  • Full audit trail of every routing decision, queryable via API
escalation/checkout-api.yml
service: checkout-api
severity:
  high:
    notify: owner
    timeout: 90s
    escalate_to: team:payments
  critical:
    notify: [owner, team:payments]
    timeout: 45s
    escalate_to: oncall:secondary
# reviewed in the same PR as the deploy

From first signal to resolved, in three steps

No dashboards to babysit. Beacon does the routing work so the response can start immediately.

1

Detect

Beacon ingests alerts from your existing monitoring — Datadog, Prometheus, or a plain webhook — and correlates duplicates into one incident.

2

Route

The owning engineer is paged directly, with the triggering metric, recent deploys, and a link to the relevant runbook already attached.

3

Resolve

Responders coordinate in a scoped incident channel that closes itself out and files a timeline for the postmortem automatically.
